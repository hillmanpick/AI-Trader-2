# 模拟执行延迟与高频边界

此检查工具仅访问原模拟账本。它测本地特征读取、策略扫描、模拟撮合及持久化，不能测 Binance 网关确认或交易所撮合。

## 已完成的模拟执行工程

- Binance 公共行情走 WebSocket；候选币盘口用 `depth@100ms` 差分重建，成交流按交易对分片。
- Redis 用于行情/特征快照。每次策略扫描对信号、候选、特征及流动性做一次 MGET；行情 freshness 仍逐字段检查。下单 sizing 和撮合单独读最新盘口，避免使用本轮开始时的旧快照。
- 模拟提交经过持久化订单状态机，读取真实盘口深度，按配置参与率、手续费、滑点模拟部分成交、过期和持仓账本。禁止用超时/价格快照伪造 fill。
- 退出订单在候选遍历中立即等待其 20ms 模拟确认，并重新读取盘口时间戳；超时仍按 IOC 规则过期。
- 分段延迟用进程内有界 reservoir 保存，不对每笔订单写监控日志。订单、fill、余额、持仓仍逐笔同步落 SQLite；信号/诊断状态只在扫描结束后批量写入。
- QQ/SMTP 通知在线程中串行发送，只保留最新状态快照。成交通知原文仍在 SQLite 事件表，worker 不等待 SMTP 网络。
- 保护单始终优先于方向信号。超过 2 秒的信号禁止开仓；平仓不读方向特征，但仍需新鲜盘口。
- 生产模拟策略按 1 秒网格评估，盘口更新时唤醒 worker。每次开仓仍执行新鲜特征、成本和风险检查。

## 查看真实模拟运行的探针

```bash
sudo docker exec ai-trader-quant-paper-worker-1 \
  python -m quant.execution_probe \
  --database /data/quant-aggressive-paper.db \
  --since-seconds 21600 --limit 500
```

探针报告窗口内最新有限条订单的成交/过期状态、零成交比率、确认及成交分位数、本地策略扫描、Redis 批量读取、SQLite 诊断提交、撮合与邮件分位数。字段 `exchange_execution_measured=false` 是刻意设计，不得把 simulated ack 延迟当成币安 RTT。延迟 reservoir 容量为每阶段 1024 个最近样本；订单和成交数来自持久化账本。

截至 2026-11-26 08:41 UTC，新 worker 的一分钟逐币策略决策间隔中位数约 1.07–1.09 秒。新 worker 自 08:34 UTC 启动以来有 2 笔模拟订单，1 笔成交、1 笔过期，样本不足以评价成交率。模拟确认 P95 约 42ms；策略扫描 P95/P99 约 69/361ms，最大观测约 1.47 秒。每秒评估不等于每秒开仓，也不含 Binance 网关或交易所撮合耗时。版本和策略政策变化使旧研究报告失效，新版本仍是未验证模拟前向测试。

## 离交易所级毫秒执行还差什么

1. 当前服务仍在 2GB、共享其他业务的 Ubuntu 服务器上，运行 Python、SQLite 和 WebSocket 行情。应迁到独立、靠近目标 Binance 订单网关的低延迟主机，再测跨区域 RTT、抖动、丢包及恢复时间。
2. 模拟策略已改为每秒评估一次，行情特征由盘口 WebSocket 更新。每秒评估不保证每秒出现交易信号。100ms 研究版本没有上线，新版本尚未通过样本外与执行回放门槛。
3. 模拟 worker 使用盘口撮合且不持有私有密钥；另一个只读账户观察器已接 ORDER_TRADE_UPDATE，并提供对账状态。私有 WebSocket 下单/撤单适配有离线测试，但生产写入硬禁用；没有通过官方 Demo/Testnet 实际发单验收。
4. 已测只读网关 RTT 和空账户主动断线恢复；真实订单 acknowledgement、成交回报、条件 Algo 订单生命周期与恢复完整性没有端到端验证，撮合队列位置也未测。
5. 低微秒/微秒级以内执行还受网卡、内核、虚拟化噪声、交易所准入及共址服务影响。Python、Docker、普通云主机无法仅凭代码升级成交易所撮合引擎；需要交易所侧的会员/共址设施，个人 API 用户通常也拿不到撮合队列前排。

优化方案优先保持 Python 做研究、风险、UI 和模拟执行。只有 profiling 证明热点后，才考虑把 WebSocket 解码/盘口增量状态机或签名发送路径移到 Rust/C++/Aeron 等低延迟服务；单纯重写语言不会弥补网络、策略优势和成交质量。ClickHouse、增加 agent 或把训练跑得更频繁都不会缩短订单网关往返延迟。

当前验收：隔离测试中的 40 笔合成模拟成交确认 P95 约 29ms，不能替代上文线上订单窗口。线上本地 100ms 目标尚未通过；Binance 真实订单延迟未测，交易所级验收未通过。这些是工程验收，不能代替盈利验证。

## 本地计算机与服务器计算（2026-11-26）

服务器到 Binance 的只读 depth 与签名 account RPC 各 30 次均成功，P95 分别约
74.7ms 与 74.6ms；模拟机上策略扫描 P95 约 53ms。当前 Windows 本地直连
`fstream.binance.com` 公共 depth WebSocket 在连接阶段超时，未收到任何行情帧。
因此当前不把本地作为实时行情/决策主节点。若改由服务器转发行情给本地再回传
决策，至少增加跨网传输延迟，且无法证明比同机扫描更快。

新增 quant.market_path_probe 可在本地和服务器只读测 Binance 公共深度事件年龄、
接入时间、帧间隔和协议错误。这只是测量，不控制交易角色。

另新增独立 AI-Trader-Compute.exe，复用服务器公开特征及完全一致的策略代码；
通过 SSH + WebSocket 传递有限输入，服务器唯一执行/记账。结果按代码、策略政策、
完整输入哈希及连接代际绑定；迟到、版本不符、断线、缓存失败均立即在服务器计算。
不迁移账户、不传 Binance 密钥、不让客户端发出下单或杠杆参数。

本地每批计算约 1 ms，但截至 2026-11-26 08:41 UTC，本地计算通道 74 个请求样本的跨网 RTT P95 约 846ms，
仍未达到 100ms 准入。因此策略判断继续在服务器本地执行，EXE 只是
可用的计算候选。停止 EXE 后服务器模拟 worker 正常运行。

原 AI-Trader-Training.exe 只负责离线训练；新计算 EXE 与其分开，不更改原训练计划。
线上模拟策略版本为 systematic-flow-second-v1，决策网格 1000ms，持仓期限和冷却期
沿用原策略参数。版本与策略政策变化使旧研究报告不能作为新版本的样本外认证。
策略继续处于未验证模拟前向测试，实盘执行关闭。线上最新一分钟每币决策间隔中位数约
1071–1087ms。服务器侧发布见 compute.compose.yaml。
